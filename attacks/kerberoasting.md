# Kerberoasting — Lab Writeup

## Date & scope

- Lab activity: September–October 2026; the recorded validation event below is dated 22 October 2026.
- Target: the author's isolated Active Directory domain `LAB.LOCAL`.
- Domain Controller: `adlab-dc01`, `10.10.10.10`.
- Attacking host: Kali Linux, `10.10.10.248` during the captured run.
- Authorization: personally owned and controlled KVM/QEMU lab; no third-party systems.
- MITRE ATT&CK: [T1558.003 — Kerberoasting](https://attack.mitre.org/techniques/T1558/003/).

## Objective

Request a Kerberos service ticket for a test service account with an SPN, extract the ticket material in a format suitable for offline password auditing, and examine the Windows and SIEM telemetry generated by the request.

## Tools used

- Impacket `GetUserSPNs.py`.
- Hashcat, mode `19700` for the AES Kerberos TGS hash format observed in this lab.
- Windows Server 2025 Active Directory Domain Services and Security Event Log.
- Wazuh 4.14.7 manager and Windows agent.

## Lab account and service

- Requesting account: `bsilverhand` (`bsilverhand@LAB.LOCAL`).
- Service account: `svc_sql` (display name `SQL Service`).
- Service account OU: `Lab-ServiceAccounts`.
- The account was configured with an MSSQL SPN on the lab Domain Controller.
- Password values and ticket hashes are intentionally omitted from this public writeup.

## Methodology

1. Confirmed that the test service account had an SPN registered in the lab domain.
2. From Kali, requested a service ticket for `svc_sql` using Impacket. The lab command used `GetUserSPNs.py`, the domain user `bsilverhand`, DC address `10.10.10.10`, `-request-user svc_sql`, and `-no-rc4`.
3. Saved the resulting Kerberos TGS material to a private evidence file. The raw file is not included in this repository.
4. Attempted offline password recovery with Hashcat mode `19700` and a lab wordlist. The lab test ultimately reported a recovered candidate; the candidate password is deliberately not published.
5. Enabled auditing for Kerberos Service Ticket Operations and repeated/checked the request so that the DC Security log contained the corresponding Event 4769.
6. Forwarded the DC Security channel to Wazuh and searched both the archive and alert data for the user/service pair.

A credential-bearing command is intentionally not reproduced verbatim. Reproduce this only in an isolated lab with your own domain and test credentials; never paste real passwords or extracted hashes into documentation.

## Findings and evidence

### Kerberos Event 4769

The matching Windows Security event was exported from the DC. Its relevant fields were:

| Field | Observed value |
|---|---|
| Event ID | `4769` |
| Event Record ID | `47783` |
| Windows Event Viewer time | 22 October 2026, 19:24:20 (DC local time) |
| Requesting account | `bsilverhand@LAB.LOCAL` |
| Service name | `svc_sql` |
| Client address | `::ffff:10.10.10.248` (IPv4-mapped IPv6) |
| Client port | `58988` |
| Ticket options | `0x40810010` |
| Ticket encryption type | `0x12` (AES256 / etype 18) |
| Session encryption type | `0x12` (AES256 / etype 18) |
| Failure code | `0x0` (success) |

The XML timestamp is `2026-10-23T02:24:20.2257363Z`; the Event Viewer display showed 22 October at 19:24:20. The exported record identifies the requester and target service as expected for the `svc_sql` request.

### Encryption deviation

The initial guide discussed RC4-based Kerberoasting examples. The actual lab request used `-no-rc4` and produced an AES256 ticket (etype `0x12`), so the appropriate Hashcat mode for the observed hash was `19700`, not the RC4 TGS mode `13100`. This is an environment-specific observation; it does not mean AES256 is immune to offline password guessing. The strength of the service-account secret remains important.

### Wazuh result

- The matching Event 4769 was found in `wazuh-archives-*`.
- No corresponding alert for that Event 4769 was found in `wazuh-alerts-*` during the investigation.
- At approximately the same time, Wazuh generated an alert for a separate Event 4624 involving `LAB\bsilverhand`, a network logon using NTLM V2 from `10.10.10.248`.
- That separate alert used packaged Wazuh rule `92652`, level 6, with a description indicating possible Pass-the-Hash.
- Rule `92652` checks for NTLM authentication as a child of a remote-logon rule. It does not inspect the `svc_sql` ticket request and is not a Kerberoasting-specific alert.

The Event 4624 is correlated by the same user, source IP, and near-identical timestamp, but that does not establish a formal causal relationship or prove Pass-the-Hash. The Kerberoasting command authenticated using the user's supplied lab password.

## Impact

An SPN-backed service account with a weak or reused password can expose service-account credential material to offline guessing after a user requests a TGS. If the password is recovered, an attacker may be able to authenticate as the service account and access resources permitted to it. The actual impact depends on service-account privileges and password strength.

## Remediation

- Use long, random, unique service-account passwords and rotate them appropriately.
- Prefer Group Managed Service Accounts (gMSAs) where the service supports them.
- Apply least privilege to service accounts; do not grant unnecessary administrative rights.
- Inventory SPNs and remove stale or unnecessary registrations.
- Monitor Event 4769 with context: requester, target SPN, source host, request volume, encryption type, and deviation from normal service-ticket behavior.
- Do not rely exclusively on RC4 etype 23 detections; AES ticket requests can still be relevant when service-account passwords are weak.

## Lessons learned

- The guide's expected RC4 signature did not describe this lab's actual ticket. The real event used AES256, which changed the Hashcat mode and required detection logic to be based on observed fields rather than tutorial assumptions.
- Event 4769 generation, archive ingestion, and alert generation are separate outcomes. Wazuh archived the attack event but did not generate a corresponding alert.
- A nearby NTLM alert must not be mislabelled as a Kerberoasting detection.
- A successful service-ticket request is not automatically malicious; requester/service context and baseline behavior are needed.
